## 一、定位与边界

### 1.1 什么是存量介入

存量介入是：带明确任务，中途进入一个完全陌生、已在运行或持续演进的项目，在不跑偏、不影响系统稳定性的前提下完成任务。

它不等同于使用项目：仅阅读 README、安装并运行已有能力属于使用，不属于介入。

存量介入的基本路径是：

```text
明确任务与权限
  → 建立项目理解
  → 按任务扩大理解范围
  → 判断影响面与稳定性风险
  → 执行与验证
  → 回填可复用认知资产
```

### 1.2 核心目标

| 目标 | 含义 |
|---|---|
| 提效 | 不从无关细节开始考古，理解范围由任务决定。 |
| 不跑偏 | 任务、交付物、边界和验收标准在对话中对齐；长程介入复用冷启动回顾。 |
| 不影响稳定性 | 先识别影响面和验证基线，再进行改动；高风险改动明确回滚条件。 |

### 1.3 任务决定理解范围

任务是连续谱，不是“窄任务/全局任务”的二分：

```text
修复一个 bug ── 新增一个能力 ── 重构子系统 ── 绘制整体架构图/业务流程图/时序图
```

摸清项目是介入前提，而不是独立目的。任务越广，所需理解的广度和深度越大；无论任务大小，都不得低于最低理解标准。

## 二、任务与权限对齐

“怎么介入、介入多深”靠需求方与介入方的对话对齐，不依赖脱离项目语境的固定规则。

开始理解或执行前，至少应对齐以下内容：

| 对齐对象 | 需要澄清的问题 |
|---|---|
| 任务目标 | 这次要解决什么问题，为什么现在做？ |
| 交付物 | 需要代码、文档、架构图、业务流程图、时序图、测试，还是其组合？ |
| 任务边界 | 明确要解决什么，以及明确不解决什么？ |
| 验收依据 | 什么状态算完成，由谁确认，需要哪些可复核证据？ |
| 介入者属性与权限 | 可读、可写、可执行、可运行测试、可访问哪些环境和数据？ |
| 稳定性约束 | 是否生产系统，是否允许停机、数据迁移、接口变更，是否可回滚？ |

任务边界与权限边界必须分开看：任务需要某项操作，不代表介入者实际拥有该项权限。

## 三、项目理解门槛

### 3.1 原则

项目理解是 LLM 上手的基石。理解能力可按任务需要逐步扩展，但任何介入任务开始前，介入方必须达到最低理解标准；否则不得编码或做结构性改动。

原因：理解不足时的胡乱编码，短期看似完成任务，长期会把治理成本推到不可接受的程度。

理解项目时始终采用全局视野：理解系统边界、协作关系与数据流转，而不是孤立阅读单个文件。

### 3.2 最低理解标准

最低理解标准必须形成以下三个**可复核、可归档的文档产物**：

| 文档产物 | 至少需要说明 | 用途 |
|---|---|---|
| **整体架构图** | 核心模块/服务、职责、边界、主要依赖和协作方向 | 防止改错层、改错模块或误碰公共能力。 |
| **数据流动** | 与任务相关的数据从何处进入，经哪些处理/服务/存储，再被谁消费或输出 | 识别状态、存储和下游影响，防止破坏一致性。 |
| **命名规范** | 目录、模块、类型、函数、接口、事件、测试等现有命名和组织约定 | 让新增内容融入项目，而不是制造新的命名体系。 |

存储逻辑属于“数据流动”的关键内容。任务涉及权限、跨服务、外部接口、数据库迁移、部署或生产数据时，必须在上述最低标准上扩展理解范围。

### 3.3 文档化与动态粒度

三项最低理解标准必须存在于项目文档中，不能只停留在对话或介入者上下文里。文档不是为凑数量而创建，拆分粒度必须按实际情况动态调整：

| 项目/任务情况 | 文档组织方式 |
|---|---|
| 任务局部、系统约定清晰、介入权限足够 | 可在一份介入任务文档中以三个章节承载架构图、数据流动、命名规范。 |
| 任务全局、跨多个服务或模块 | 应拆为独立架构图、数据流动/时序图、命名规范等文档，确保可审查和复用。 |
| 命名混乱或历史包袱重 | 命名规范按大层级/子系统分别记录；必须标注统一约定、层级局部约定、历史例外和冲突，不能强行虚构单一规范。 |
| 介入方修改权限不足 | 用更完整的理解、影响面和建议文档补足交接信息；明确“建议改什么、为什么、证据是什么、由谁执行”，不能假装已完成修改。 |

文档的最低要求是可复核、可追溯、可被后续介入复用；文件数量不设固定目标。

### 3.4 渐进式 draw.io 图谱

> 本节为已确定的方法论补充，作为 3.2 与 3.3 的落地形式；整体架构图与数据流动统一以可渐进补全的 `.drawio` 资产承载。

**资产载体**

三项最低理解标准的承载方式：

| 理解标准 | 承载方式 |
|---|---|
| 整体架构图 | 以可渐进补全的 `.drawio` 图谱承载 |
| 数据流动 | 以可渐进补全的 `.drawio` 图谱承载 |
| 命名规范 | 仍以 Markdown 文档为主，可用目录层级图（`.drawio`）辅助 |

选择 `.drawio` 而非一次性画成静态图的原因：结构化、可编辑、可复用；介入过程中能逐层补充与修正，不必整图重画。

**分层补充顺序（从全局到细节）**

图谱按以下顺序逐层补全，每完成一层即可据此进入执行或继续下一层：

```text
① 全局架构骨架：系统边界、核心模块/服务、主要依赖与协作方向
  → ② 任务相关模块/服务边界与依赖：圈定任务影响面
  → ③ 任务数据流：数据从哪进入，经哪些处理/服务/存储，被谁消费或输出
  → ④ 必要时：时序图、接口/事件、存储与部署细节
```

- 最低理解标准的达标形态：整体架构图 = ① + ②，数据流动 = ③；④ 是任务相关时才补充的可选项，不影响最低标准判定。
- 骨架先于细节：先确认系统边界与模块归属，再落任务相关细节，避免在错误分层上画细节。
- 数据流以 ② 圈定的范围为边界，不画与任务无关的全局数据流。

**事实、假设与待确认的标识**

图中每个节点和连线都必须能区分三类状态，不允许把未验证推测伪装成事实：

| 状态 | 建议表示方式 | 含义 |
|---|---|---|
| 已验证事实 | 实线 / 实色 + `[已验证]` 标签 | 有代码、配置、测试、命令输出或运行行为佐证 |
| 暂定假设 | 虚线 / 弱色 + `[假设]` 标签 | 由目录名、文件名、配置名等线索推断，尚未交叉验证 |
| 待确认项 | 占位节点 / 高亮 + `[待确认]` 标签 | 存在但情况不明或存疑，需与项目方/需求方确认 |

- 上述表示方式为建议默认，具体线型、颜色或标签前缀由介入方按团队习惯约定，不强制统一。
- 每个元素可附证据来源：README、源码文件路径、配置文件、测试、命令输出或对话确认记录，写入元素备注或挂接链接，供后续介入者复核。
- 标注为 `[已验证]` 的内容可随证据增强而细化，但未经验证不得升级为事实。

**拆分与层级组织动态调整**

不强制单一图或固定文件数量；按任务范围、系统复杂度、介入权限动态调整：

| 情况 | 图谱组织方式 |
|---|---|
| 任务局部、系统约定清晰 | 单份 `.drawio` 内用多页（page）承载各层级 |
| 任务全局、跨多个服务或模块 | 拆为独立 `.drawio` 文件或独立页，按层级组织，确保可审查与复用 |
| 命名混乱或历史包袱重 | 图上如实标注 `[待确认]` / `[假设]` 区域，不强行画满；命名规范层面的处理见 3.3 |
| 介入方修改权限不足 | 图谱作为理解与影响面证据交需求方或有权限者，明确建议改什么、证据是什么、由谁执行 |

层级组织与拆分可随理解加深在介入过程中调整，不需要一开始定死。

### 3.5 双读者文档（作者实测修正，2026-08-19）

项目文档分两类读者，承载方式不同：

| 读者 | 用途 | 承载方式 | 要求 |
|---|---|---|---|
| **给 AI 看** | 精确、可复核、可程序化消费 | Markdown 为主 | 结构、路径、证据、字段准确；AI 能据此判断和施工 |
| **给人看** | 帮助人类建立对项目的认知 | 渐进、可读、由粗到细 | 一次只扩展一层认知，不一次性抛细节 |

**人读文档的渐进认知原则**：人的理解深度是逐步建立的。首次阅读应先建立系统整体认知（系统是什么、边界在哪、大致怎么协作），再按需逐层深入。**不要把“4-5 层文件夹下的某个具体内容”作为初次阅读的起点**——理解深度不够时，孤立细节看了也会忘，等于没有价值。细节适合复习回顾，不适合初次建立认知。

**由粗到细的扩展顺序（与人读对应）**：

```text
整体认知（系统是干什么的、核心边界）
  → 关键协作（模块怎么配合、数据大致怎么流）
  → 任务相关区域（本次介入需要动的地方）
  → 具体细节（接口、字段、文件路径）
```

**判定**：一份理解文档如果让一个对项目陌生的人读完后能回答“这个系统是什么、我要碰的部分在哪”，才是合格的初次阅读材料；如果读完后只有一堆互不关联的具体路径，说明它把“回顾性细节”当成了“入门材料”，需要重写为渐进式。

注意：**给 AI 看的 Markdown 和给人看的渐进文档是同一事实的两份视图，不能各写一套互相矛盾的内容**。事实保持单一来源，差异只在呈现方式和粒度顺序。

**落点：`doc/protocol/README.md` 默认即人读入口**。初始化模板生成的 `doc/protocol/README.md` 默认就应带「一页看懂（渐进总览）」骨架——一页看懂系统是什么、模块职责与边界、关键协作，最后才指到 `understanding/*`、`modules/*` 等细节底稿，并明确标注「这些是给 AI / 深入查阅的细节底稿，人读先看本总览」。`understanding/`、`modules/` 默认定位为 AI/深读底稿，不作为人读起点。二者内容同源、不能矛盾（单一事实来源），差异只在粒度与呈现顺序。

**判定（人读入口）**：`doc/protocol/README.md` 若让陌生人对系统仍无整体认知（只有目录链接或深层路径），即为不合格，需重写为渐进总览。appcode 存量介入即因首次生成的是纯目录式 README 而暴露此缺口（2026-08-20 修正，见插件模板 `templates/common/README.md`）。

### 3.6 项目理解的证据链

理解必须从线索走向验证，不能把推测写成事实：

```text
README / 项目文档提出初始假设
  → 目录、文件名、配置名补充线索
  → 入口、构建配置、依赖关系、测试与关键实现交叉验证
  → 形成可复核的架构图、数据流动、命名规范
```

| 项目状态 | 起点 | 必须注意 |
|---|---|---|
| 有 README 或正式文档 | 从文档获得定位、运行方式、入口和已有约定 | README 是起点，不是完整架构事实；仍需与代码和配置交叉验证。 |
| 缺少 README 或文档不足 | 从目录、文件名、配置文件提出暂定假设 | 文件名是线索，不是证据；必须继续验证。 |
| 文档与代码冲突 | 以可执行配置和实际代码行为为准，记录文档滞后 | 不能盲信文档，也不能无记录地静默替换结论。 |

### 3.7 “真的理解”的对话验证

LLM 不可用“我已经理解”自证。应通过对话审查其文档化理解产物，例如：

- 让其指出任务从哪个入口进入、经过哪些关键模块、可能影响哪些下游。
- 让其解释新增能力按现有命名约定应放在哪里、应如何命名，以及为什么不应放到相邻目录。
- 让其区分已验证事实、暂定假设和待确认项。

理解产物必须形成项目文档，但图、表、文字说明和结构化复述可以组合使用；关键是可复核、可追溯，且文档粒度与实际项目和任务相称。

## 四、任务性质、系统状态与风险

### 4.1 任务性质

| 类型 | 说明 |
|---|---|
| 纯文档 | 架构图、业务流程图、时序图、调研或理解报告；通常不改代码，但理解范围可能全局。 |
| 纯代码 | 修复、增强、重构；需要明确改动边界和验证。 |
| 混合 | 先完成理解产物，再进行代码或配置改动；最常见。 |

### 4.2 系统状态与介入者条件

在任务对齐阶段同步考虑：项目规模、成熟度、文档和测试完备度、技术栈复杂度、运行约束，以及介入者的角色与权限。

这些是任务参数，不预设为固定流程分支；它们决定需要补充多少理解、验证和人工确认。

### 4.3 稳定性风险维度

| 风险维度 | 需要判断的内容 |
|---|---|
| 影响面 | 改动是局部模块、公共组件、跨服务契约，还是全局行为？ |
| 破坏性 | 是否涉及不可逆数据、接口兼容性、权限或外部系统？ |
| 回滚能力 | 是否可以借助版本控制、配置开关、迁移回退或发布策略恢复？ |
| 可验证性 | 是否有存量测试、可运行环境、可观测输出；缺失时如何建立最小验证？ |

## 五、独立验证方

### 5.1 定位

存量介入可配独立验证方（检察子 agent）检查介入方是否按规程满足证据门槛。它不保证代码绝对正确；它验证的是：介入方有没有在理解达标、边界清楚、影响面可控的前提下进入下一阶段。

### 5.2 独立性硬条件

> **检察者的规则来源、输入材料、判断权限和输出通道，不能由被检察者控制。**

| 维度 | 独立验证方要求 | 要防止的问题 |
|---|---|---|
| 规则来源 | 在任务开始前注入稳定提示词，来自规程、用户或项目规则；不由主 agent 临时改写 | 被检察者降低标准或改变检查范围。 |
| 输入材料 | 直接读取仓库、配置、命令输出、提交、测试结果和任务记录 | 被检察者只挑选有利材料。 |
| 判断权限 | 只判断证据是否满足门槛，不替介入方设计、施工或补写答案 | 检察者变为协作者，失去独立性。 |
| 输出通道 | 结论直接交需求方，或写入被检察者不能篡改的审计记录 | 被检察者过滤、改写或忽略结论。 |

独立验证方的边界是“看 + 判 + 说”，不是“替做”。这与冷启动回顾的只读边界一致。

### 5.3 最低能力基线与验证职责

独立验证方可使用低成本、本地部署模型作为最低能力基线。当前实践候选为 `testcoder` 子智能体所用的本地 `ornith-1.0-9b:latest` 模型；截图已独立核对的实际配置如下：

| 项 | 实测值 |
|---|---|
| 架构 | `qwen35`（Qwen3.5 微调版） |
| 参数量 | 9.0B |
| 量化 | `Q5_K_M`（约 6.0 GB，显存 7-9 GB） |
| 原生 / 实际上下文 | 256K / 32K（`num_ctx=32768`） |
| Embedding 维度 | 4096 |
| 采样参数 | temperature=0.7 / top_p=0.9 / top_k=40 / repeat_penalty=1.05 |

验证目标不是证明它能替代更强模型施工，而是验证：这种最低配置能否稳定检查介入方是否遵循本方法论的证据门槛。

若最低配置在真实任务中能够稳定完成遵循度验证，就不应把更强模型视为本方法论成立的前提；若失败，必须记录失败点（提示词、证据可读性、上下文、判断能力或平台限制），再决定应补机制还是提高模型能力。

首次试用（2026-08-17）：本地 `testcoder` 对插件遵循度做只读审查，发现了批准范围的解析边界（尾部斜杠和范围列表终止），修复后守卫测试由 13 项扩至 15 项且全绿。这证明最低配置可发现真实实现问题；稳定性和误报率仍需在更多任务中验证。

### 5.4 建议守的三个门槛

为控制治理成本，独立验证方不必全程常驻；优先在三个关键门槛出现：

1. **最低理解标准完成后**：三项理解产物是否有证据、是否混淆猜测与事实、是否允许进入执行。
2. **改动方案与影响面明确后**：任务/权限边界、公共契约、风险和验证计划是否清楚。
3. **交付验证后**：是否保留了可复核证据，是否满足任务验收、未越出人类可兜底的责任边界。

## 六、执行、稳定性验证与项目理解文档更新（待实测细化）

### 6.1 稳定性的真实判据：人类可兜底边界

AI 的职责是帮助人类解决问题，不是替人类承担不可控后果。一次介入是否“没有变得更差”的首要判据不是 AI 自己声称测试全绿，而是：**改动是否影响了介入者所属人类权限、责任与兜底能力之外的内容。**

只要问题仍在负责人的可见、可判断、可确认和可修复边界内，人类就能兜底；一旦可能越出该边界，后果无法由当前负责人承担，就必须在改动前升级确认。测试、构建、回归和历史基线是重要证据，但服务于这一判据，不能取代人类责任边界。

### 6.2 项目等级决定谨慎程度

| 项目/场景 | 可接受的介入方式 | 稳定性要求 |
|---|---|---|
| 个人项目、实验项目、可整体重构的烂项目 | 可在版本控制和基本验证下快速迭代；即使 bug 逐步累积，仍可由负责人重构或重建 | 保证不无意影响边界外内容即可；治理成本可相对低。 |
| 团队内部系统、可控环境 | 小步改动，保留验证证据；出现不确定问题先问实际维护者 | 负责人应能看见影响、确认结果并执行回滚或修复。 |
| 已上线生产级项目 | 改动必须微小、谨慎、可解释；优先局部修复，避免顺手重构或扩展任务范围 | 不得越过权限、服务边界、数据边界、公共契约或发布责任边界；不能确认可兜底时不得执行。 |

项目等级不是预设标签，应由任务与权限对齐时结合实际运行状态、用户影响、数据敏感性和回滚能力确认。

### 6.3 问题升级与人类确认

介入中发现问题时，处理原则是按人类权限边界升级：

```text
当前负责人能确认并兜底
  → 记录事实，继续在边界内处理

当前负责人无法确认 / 需要更多项目事实
  → 询问维护者、需求方或实际知情人

问题频繁出现、涉及跨团队责任或可能越出当前权限
  → 找项目负责人/领导确认，暂停越界改动
```

AI 必须把“已验证事实、暂定假设、待确认项、可能影响的边界”说清楚；不能因为想推进任务而把需要人类确认的问题伪装成可自行解决的问题。

### 6.4 影响面与辅助验证

在不越出人类可兜底边界的前提下，介入前至少要能回答：

- 改动直接落在哪个模块、服务、配置或文档？
- 上游触发者和下游依赖者是谁？
- 是否涉及存储、权限、外部服务、公共契约或发布路径？
- 当前负责人是否有权限观察、验证、回滚或修复这些影响？
- 哪些已有测试、构建、运行或人工检查可以作为辅助证据？
- 若验证失败，谁以什么方式回滚或继续处置？

存量介入可复用新启动规程中的小步提交、动态测试、关键路径禁 mock、覆盖率、回归和验收锁，但验证强度必须随项目等级和人类可兜底边界调整，不把形式化测试数量误当作稳定性本身。

### 6.5 项目理解文档更新

每次介入结束后，更新本次已经验证、且对后续介入有价值的项目事实：模块边界、关键数据流、命名约定、红线、未解决风险、升级记录和验证证据。

最低原则：**只更新这次已验证、对后续介入有价值的事实；不强制为每次小改动额外造文档。**

目标不是增加文档数量，而是避免下次介入又从零猜测；理解文档更新后，才成为后续介入可复用的项目资产。

## 七、待实践验证

本草案不视为正式规程。需要通过真实项目验证以下问题：

1. 最低理解标准在不同规模和技术栈项目中是否足够、是否过重。
2. 三个独立验证门槛是否有效，是否会造成过高治理成本。
3. “人类可兜底边界”如何与影响面分析、辅助测试和回滚安排共同落地，尤其是测试不足的项目。
4. 文档型、代码型和混合型任务是否需要不同的介入流程分支。
5. 是否能在不影响稳定性的前提下完成一次可复现的介入任务。
6. 全局插件的项目区问卷、文档骨架、代码写入守卫和人类批准/豁免是否能在真实 ZCode 客户端按预期协同；本地脚本和临时项目状态机实测见 `doc/experiments/2026-08-17-protocol-project-area-plugin.md`。
